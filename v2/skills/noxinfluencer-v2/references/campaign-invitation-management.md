# Campaign Invitation Management

Use this workflow to manage the current Campaign's pending/sent creators, invitation settings, collection imports and dispatch state. Read the Campaign and current invitation state first. Adding creators to invitation pending or importing a collection does not send email. Preserve returned creator identities, page boundaries, failure reasons and unavailable metrics.

For showing completed work in the SaaS Campaign workspace after the final answer, use the page-coordination guidance in `{baseDir}/references/campaign-agent-automation.md`. Showing invitation settings or a send preview does not confirm sending.

## Settings and copy

Read `settings-get` before changing settings. The plan scope and a single-creator `target` scope are different. The Agent may generate and revise subjects, bodies and round content when the user requests it. Settings bodies use readable UTF-8 text, including `emailContent` and `emailContentText`; the adapter handles editor encoding. Preserve the existing settings structure and fields the user did not change. Use `settings-save` to save a draft; use `settings-apply` only when the user authorized applying it. Saving or applying settings is not authorization to send.

Read the current command schema for known field types, choices and text limits. Incomplete drafts may keep declared unset values; a filled field must use its declared wire value. Do not mix conflicting sender-type aliases or substitute display names for enum codes. Preserve exact account IDs as strings, including values above JavaScript's safe integer range.

Do not Base64-encode the copy yourself. The runtime checks both readable arguments and the actual encoded upstream draft before beginning the mutation. Encoding can increase request size, so a field within its own text limit can still exceed the whole-request budget. On that error, revise the oversized content within the user's request; do not silently truncate it, split one complete draft into unrelated writes, or retry an unchanged payload.

Adjacent completed round coordinates must produce an exact signed 64-bit millisecond interval for every possible first-send clock. Negative, fractional and nonincreasing day values remain supported; do not round a fractional millisecond or guess a different schedule format. An incomplete draft may keep declared unset fields.

The runtime requests the compact editor response, retaining complete readable `draft`/`applied` content and editable history while omitting duplicate wire/execution copies. The final budget also includes the tool protocol's structured result and escaped text copy. An `OUTREACH_RESPONSE_TOO_LARGE` / `97080` rejection occurs before settings writes; use the campaign page to reduce the full settings as authorized by the user. Do not retry under a new key or silently remove copy to make it fit.

Use `sender-options` to select an existing authorized sender; never invent its ID. First-send/resend previews identify creators and contact availability but withhold internal email addresses, because a preview does not unlock contacts. Do not infer or disclose the hidden addresses.

Copy the returned `invitation_sender` object into `settings.sender`: its canonical fields are `type` (1 Gmail, 2 enterprise, 3 Nox, 4 Outlook) and `authInfoIds`. Keep the selected Nox business sender IDs and order. If both `authInfoIds` and `senderIds` are present, their nonempty selections must match after ordered deduplication; conflicting lists are rejected. An empty alias does not erase the other selection. Generic email sender-type fields are not the Campaign settings contract. The adapter normalizes supported aliases and rejects conflicting types. Do not ask the user to reconnect a valid account solely because a field was missing.

For an upstream business error, use the returned `category`, `upstream_error_num` and `recovery` to choose the next step. Dependency failures and timeouts do not imply malformed parameters. Preserve the request ID when reporting a failure; do not repeatedly rewrite a valid draft or resubmit a mutation with an unknown outcome under a new idempotency key.

First-send mode is `immediate` or `creatorLocalTime`; the latter uses `firstSendTime` as `HH:mm`, including `24:00`. Round `roundTimeEnum` is a half-hour slot 0–48, or 999 for the previous successful send's local clock time. `roundDays` is a nominal day value; preserve the returned round sequence rather than requiring increasing days. Business round counts are not capped; runtime payload limits still apply. Use `settings-reset` only when the user wants to discard unapplied edits; it preserves applied settings and sent history.

Single-creator edits only change permitted unsent copy and timing. They do not change the plan sender, attachments, products or round structure, and cannot rewrite sent history. Reuse existing authorized email attachment references; this workflow does not add chat attachment parsing. Read `sequence` or `recipient-preview` for existing journey content; use the send preview for the actual proposed sending action.

Use `detail` to inspect actual frozen journey history. A null `recipient` in a configuration preview means no materialized unsent receiver was returned; it does not prove that the creator has no contact email. Use the dedicated `preflight` operation on the exact selected creators for authoritative contact and quota diagnosis. `readiness` checks plan configuration only and cannot replace selection-specific preflight.

## Contact visibility and invitation eligibility

When the user asks to invite selected pending creators, follow the Campaign page's invitation checks: run the dedicated selection-specific `preflight`, then continue through the sending preview, confirmation and execution below when the checks permit it. An email that is locked, masked, absent from a list or null in another response is not evidence that the creator has no email or cannot receive an invitation. Do not reject or remove that creator from the requested selection on this basis.

The invitation backend decides whether contact unlocking is required and whether sending is allowed from the current account's data and entitlements. Do not require the user to unlock contacts or provide email addresses first. Do not call creator profiles, contact lookup, contact unlock or other unrelated interfaces to independently validate invitation eligibility or reveal addresses. Keep these decisions in the native invitation workflow.

Use only the invitation preflight and send preview's explicit eligibility results, blockers and skip reasons. If they permit sending, proceed without adding another contact-data check. If they block the operation, explain the returned reason and resolve it within the invitation workflow before a fresh check. A missing or failed invitation check is not permission to guess eligibility or switch to another sending route.

## Sending requires a second confirmation

1. Select an explicit list of 1–100 creators for `start`. Never omit targets to mean all pending. Handle larger selections in separately reviewed batches. `resend` and `retry` take exactly one creator per preview.
2. Run the dedicated `preflight` for a `start` selection, then request a sending preview with the unchanged action and targets. The sending adapter also repeats the mandatory preflight before creating an executable review. `start` sends pending creators. `resend` creates a new invitation using the latest applied plan and clears old personal overrides. `retry` resumes the current explicitly failed round with its frozen content. Do not substitute one action for another.
3. Show the returned recipients and contact availability as explicitly classified by the invitation checks, sender, subject and body, attachments, rounds/timing, and relevant preflight warnings. Describe missing-contact skips only when the invitation preflight or send preview explicitly reports them; hidden or unrevealed addresses alone are not missing contacts. A managed sender may be assigned by the backend pool at execution; do not invent its final address. If the preview is blocked, explain the returned blockers and correct them before requesting a fresh preview.
4. Wait for an explicit second user confirmation of this review. The original request to invite creators, permission to draft copy, an automation setting, and possession of a preview token do not constitute that confirmation. The reference is issued before human confirmation; it is not evidence that the user has agreed.
5. Only then execute the reviewed operation with the unchanged business arguments, returned token, stable attempt identity and explicit confirmation. The token expires within five minutes, is bound to the authenticated user, client and Campaign, and permits one execution attempt. Use the runtime adapter for exact fields. The backend rechecks current effective content and targets. Changed content, expired references or rejected state require a new review and confirmation.
6. `accepted` means the operation was accepted, not that mail was sent or delivered. Use `send-result`, the task reader or the invitation list to report progress. On timeout, in-progress or `unknown`, do not create another preview to bypass the consumed reference and do not resend. Reconcile authoritative task/list state first. Never automatically retry a creator in UNCERTAIN, replied, opted-out or protected cooperation state.

## Other page operations

- List `pending` or `sent` with the declared status filter and pagination; use the same `min_sub`, `max_sub` and `regions` in list/count and all-matching cancellation. `regions` reads the available region choices for that journey. Unknown values remain unknown.
- Import a selected collection subset or an explicitly authorized whole collection. Explicit targets must belong to the selected platform. `select_all: true` covers all four supported platforms in the collection, so do not use it to mean all creators on only one platform. Preserve returned `successCount` and `failureCount`; the latter includes skipped identities. A later batch can fail after earlier batches committed. On `COLLECTION_RECORD_CORRUPTED` / `97083` or an unknown result, inspect the original attempt and current invitation list before addressing the unfinished scope; do not assume the whole import wrote nothing or repeat it under a new key.
- `state` pauses/cancels a task or one creator; `cancel_failed` requires a creator. A creator pause ends outstanding rounds and restores preparation; a task pause stops dispatch while preserving its frozen rounds. A paused task can be explicitly cancelled. There is no generic resume endpoint. For bulk cancellation, follow the batch scope below.
- `automation-get`/`automation-switch` read or change only the existing invitation switch. Enabling it is not authorization for an immediate send. Do not add an Agent loop, recurring Agent task or promise that scheduling is implemented beyond the backend's actual behavior.

Use only tools available on the connected runtime. If the provider has not deployed these contracts, report that gap without claiming success or falling back to generic email sending.

## Bulk cancellation of waiting or queued invitations

Use one `state` call with `action: "cancel"` and `targets` containing 1–1000 distinct creator identities. Copy returned `creator_id`, or the returned raw `channel_id` and numeric `platform`. The adapter submits one request to the server's bulk cancellation transaction. Never loop the single-creator `target` operation, and never substitute candidate removal, collection deletion or contact opt-out.

Keep the Campaign selected by the current SaaS page or conversation. The user's explicit cancellation request authorizes its stated scope; do not ask for the same approval again. For the queued list, set `status_group: "queued"` explicitly. Omitting it, or using `waiting`, retains strict waiting-list cancellation. This field is only valid for batch scopes, never a single `target` or `task_id`.

For an explicitly authorized selection of all matching waiting or queued invitations, use `all_matching: true` and `expected_count` (1–1000), with the same `status_group` and exact `min_sub`, `max_sub` and `regions` filters of that selection. Do not invent the count or silently drop a filter. If the matching count is not known, read the matching page/count before execution; if the connected runtime cannot obtain it, report that limitation. Do not page through the full list to simulate a server batch.

Choose exactly one scope: `target`, `task_id`, `targets`, or `all_matching`. Batch scopes only support `cancel`; filters and `expected_count` belong to `all_matching`. Never split an oversized selection automatically. Keep a stable `idempotency_key` for the same attempt; a transport timeout is an unknown outcome, not evidence that no cancellation occurred.

Sending continues during queued cancellation. The backend cancels eligible queued work and skips creators already sent, sending, uncertain, replied or otherwise no longer cancellable. Report returned `cancelledCount` and `skippedCount` separately, including zero cancellations when all rows were skipped; do not report the requested count as the cancelled count or claim sent messages were recalled. Existing successful history remains; eligible future queued rounds can still be cancelled.

For queued `all_matching`, a shrinking queue is accepted and missing creators contribute to skips. Growth beyond the authorized `expected_count` is rejected. Waiting cancellation retains strict selection checks. On a selection or lock conflict, reread current state and revalidate scope rather than changing counts or retrying blindly. Do not retry skipped creators through a single-cancel operation or by switching to waiting. If all rows were skipped, report no cancellation and refresh the list without claiming a data change.
