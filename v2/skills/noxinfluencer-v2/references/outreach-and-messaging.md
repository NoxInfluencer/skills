# Outreach And Messaging

## Choose Email Task Or Message Thread

Use an email task for first outreach to selected creators. Use a message thread for replies, scheduling, or archive actions after a conversation already exists. If no thread exists, do not fabricate one; offer the email-task workflow instead.

Platform outreach can add recipients by creator identity without retrieving visible contact details. External outreach requires the user to request visible contacts explicitly.

## Review Before Send

Before any send or schedule, read and summarize the exact task or thread, effective recipients, sender, subject, body or message content, attachments, and scheduled time. Do not draft or materially rewrite outreach copy unless a separate approved content workflow supplies it.

The user's approval must cover the effective recipient scope, sender, content, and timing. A manager's reported approval, a prior generic request to "send it," or urgency does not replace the current user's confirmation of the exact send state. Any change after approval requires a fresh preview and confirmation.

## Attachments And Content Roles

Distinguish public rich-text images from private attachments. Preserve attachment identity and role, and remove only the selected attachment. Do not expose private attachment locations as public content links.

Adding or removing an email attachment automatically cancels any scheduled send for that task. Read the task back after the attachment change, report the canceled schedule, and require confirmation again before scheduling or sending the updated content.

Collaborator changes should use incremental add/remove by default. Use replace only when the user explicitly resets the entire group, and preview the complete resulting collaborator set before applying it.

## Batch And Scheduled Sends

Bulk send is high risk. Present total recipients, deduplicated recipients, suppressed or invalid recipients, sender, content digest, and schedule before execution. Execute one approved job when the capability supports batching; avoid one send request per recipient.

For scheduled work, report the authoritative scheduled time and timezone. Cancel or reschedule only the selected job and confirm the previous and new state. Preserve provider-returned partial failures and do not claim success for skipped recipients.
